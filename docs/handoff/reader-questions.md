# Reader questions (deduplicated by area) -- decisions already taken are in handoff-new-project.md

## webapp
- Search fallback and L4 free answer. When the engine abstains, has no map or is down, the Diagnostic falls back to AI Search plus a GPT-4o judge and guide draft. L4/OPEN gives a free-form RAG answer through orchestration/answer.py. Keeping either keeps AI Search, idx-<client>, the skillsets, the enrichment Function and answer.py. Recommendation: drop both in the new project. L4 then says 'aucune fiche validée' (rephrase, or a technician adds a reference question), and an engine outage shows an explicit 'moteur indisponible' notice. The Web App then needs no Search at all.
- Model calls made by the Web App itself (variable extraction on every message, screenshot reading, step help on 'Expliquer'/'Ça ne marche pas'). They decide nothing, but they need gpt-4o and the Cognitive Services OpenAI User role. Recommendation: keep screenshot reading and step help (help is grounded in the fiche and labelled as such). Decide whether extract_variables should keep appending model-read values to the text sent to /kecore/find, or let the Function's own interpretation do it alone (more deterministic).
- ITSM action module (/itsm tab, itsm/poll, propose, execute Logic Apps, kv-ke3-itsm-delivery, Graph app roles, demo identities and tickets). Keep it in the new project or leave it out? Recommendation: leave it out of the first clean deployment and add it back later as a separate optional module. Before removing it, move the access block that labels, dictionary and review take from config/itsm.yaml into config/labels.yaml.
- Diagnostic write-back to ServiceNow and the handover (V10 slice 6, dry run, Logic App logic-diag-writeback-client-s). Keep it? It needs the ITSM agents group, a ServiceNow instance and a Key Vault secret. Recommendation: keep it only if ITSM is kept; otherwise remove the route, panel, table and config together.
- Same Entra tenant (KnowledgeEngineV9655, a50d938b-...) with only a new subscription, or a new tenant? This decides whether the tenant and group IDs in config/*.yaml and clients-local/engine.client-s.yaml, the App Registration (redirect URI, groupMembershipClaims, client secret) and the external tenant 7bb131d8-... still apply. Recommendation: say which, because a new tenant means new groups and a new App Registration.
- New global-name prefix. The disabled subscription still holds stknowledgeengine3v9, app-knowledgeengine3-v9, srch-/aif-/kv-knowledgeengine3-v9 and kv-ke3-itsm-delivery (Key Vault names stay reserved through soft delete). Runbook §12.1 already had to move from knowledgeengine2 to knowledgeengine3 across 27 files. Recommendation: pick a new prefix, and remove every name from the Python code (Table endpoint, plus Search/AOAI endpoints if kept) by passing them as app settings from Bicep outputs, so the next move changes only a parameter.
- Synthetic demo clients clienta/b/c and demo/. No kecore map was ever built for them, and the only real client (client-s) lives in git-ignored clients-local/. Recommendation: remove config/engine.client{a,b,c}.yaml, demo/ and kb/eval with the RAG. Rebuild one synthetic client through kecore only if a public showcase without real data is wanted.
- Who may label, review and decide the dictionary and the routing? Today it is the ITSM agents group (KE-v9-itsm-agents), through the itsm.yaml fallback. Recommendation: a dedicated Entra group in config/labels.yaml.
- Classic assistant archive (/classic, /c/<id>, tables convindex/convturns). Recommendation: remove it, since there is no saved conversation to carry into a new subscription.

## engine
- Remove the three local CLIs (`python -m kecore|kefind|scoreboard`), the old 5-step kefind pipeline (engine, compose, decide, graph_filter, calibration, understand, most of search.py) and the local scoreboard tooling (importers, labeling, ids, search_baseline)? Recommendation: yes. CLAUDE.md forbids writing engine data under clients-local/, the spec already plans it (slice 7), and none of it is reachable from the Function. About 2,000 lines of code and about 100 tests go.
- Keep `POST kecore/funnel-config/apply` and the word-mode floor? scoreboard_service.apply refuses whenever the served map has a semantic index, which is the default, so today it is dormant. Recommendation: keep the word-mode decision itself (it is /find's fallback when the index is missing or degraded), and keep the apply route only if non-semantic runs (`semantic: false`) stay a supported mode; otherwise remove it.
- Keep `POST kecore/tickets/rescrub`? It was added for a one-off privacy migration of 370 rows (runbook §18.5). Recommendation: keep it. It is small, and because the raw export is deleted after scrubbing, it is the only way to apply a stricter cleaning rule to stored rows without asking the client for a new export.
- Give passes B and C their own deployment through KECORE_AOAI_BATCH_DEPLOYMENT (for example `gpt-4o-enrich`), and set it in kecore.bicep? Today all engine calls share the 30 kTPM gpt-4o deployment with the live assistant. Recommendation: yes if the V9 AI-Search enrichment Function is dropped from the new project, because its 20 kTPM `gpt-4o-enrich` quota is then free. Do it in Bicep, not by hand, because a kecore.bicep redeploy replaces the app settings.
- Naming: the disabled subscription still holds the global names (storage account, Key Vault with soft delete, Foundry subdomain, *.azurewebsites.net hosts), so a new prefix is mandatory. Should the new project also drop the `-v9` suffix and the `knowledgeengine3` defaults baked into kecore.bicep, kecore-link.bicep and deploy-kecore-function.ps1? Recommendation: one prefix parameter everywhere, with no name hard-coded in a script default.
- Recover human-made data from the disabled subscription, if its storage is still readable: ticketlabels, refquestions, kefindpending decisions, dictionary-decisions.json, exclusion-config.json. Recommendation: try. These do not depend on the model host and cannot be rebuilt from git. Do not bother with llm-cache/, embed-cache/, find-cache/ or old runs: their keys and index model ids include the old Foundry host, so they would not match.
- Simplify the orchestration code that only exists so that orchestrations scheduled by older deployments replay correctly (`llm_parallelism`, `routing` and `catalog` checks in function_app.py)? Recommendation: optional and low priority. A new task hub has no history, but the change touches orchestrator determinism and its tests.
- Ticket intake hard-codes the EasyVista French CSV format (`;` separator, column allowlist in kecore/tickets.py). Recommendation: keep it as is for client-s, and only add a per-client column mapping when a second ITSM export format actually arrives.
