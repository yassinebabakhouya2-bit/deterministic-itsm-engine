# Gotchas recorded by the readers (to keep in the new operations guide where they still apply)

## data
- Every model record key holds '<deployment>@<host>' (kecore/llm.py:237-246, function_app.py:166-168). A new Foundry account name means no replay, so the first kecore run in the new tenant must be mode 'record'. In 'replay' every call is an error.
- A restored semantic index (runs/<run>/semantic) is refused because the embedding model id differs (kefind/route.py:108, 'model_mismatch'), and /find falls back to degraded word decisions. Never restore runs/ or latest.json: run kecore again.
- The RAG fallback filters `clientId eq '<client>'` (orchestration/answer.py:709/805), taken from blob metadata clientid (search/skillset*.template.json:70). Transcripts also need sourcetype=audio or video. upload-batch without metadata makes the documents invisible, so replay the manifest metadata (block 4a).
- A raw audio blob without transcribed=true is transcribed and billed again: Speech plus Language PII and summary, about 1.5-2 min per file, one at a time, 118+ files. A video without videoindexed=true in an empty Video Indexer account is indexed again (85 min). Restore the flags before the transcribe and video Logic Apps run for the first time (firstRunUtc is 1 h 30 after deployment).
- ticketlabels.skipped must stay an Edm.Boolean. scoreboard_service.labels_of uses `if row.get('skipped')`, so the string 'False' silently drops every label from the scoreboard. Never re-import with az storage entity insert: it casts numeric strings to int or float, needs key@odata.type for bools, and goes through az.cmd's 8191-character command line.
- Windows PowerShell 5.1: az output captured in a variable corrupts non-ASCII characters (U+FFFD) whatever chcp, PYTHONUTF8 or PYTHONIOENCODING say, because az.cmd runs python -I. For data and names, use REST with RawContentStream and write bytes. Never write JSON with > or Out-File (UTF-16LE) or Set-Content (ANSI). Read with -Encoding UTF8. Out-File -Encoding utf8 adds a BOM, which kecore accepts for dictionary-decisions.json and exclusion-config.json (utf-8-sig) but which is best avoided elsewhere.
- PowerShell 7 ConvertFrom-Json turns ISO date strings into DateTime, which can change labeled_at or decided_at when written back. Windows PowerShell 5.1 keeps strings: run the table import under 5.1, or under PowerShell 7.5+ with -DateKind String.
- In double-quoted PowerShell strings, $filter, $top, $select and $St.table are expanded or cut. Keep OData parameters in single quotes or build the URL by concatenation.
- `az account list` without --all hides Disabled subscriptions (azure-cli list_subscriptions keeps only state 'Enabled'). The checks in runbook §19.21 therefore print nothing for the disabled subscription.
- /tickets/scrub reads only tickets-<client>/raw/*.csv (tickets_service.py:69), although runbook §15.3 lists CSV/XLSX/JSON/JSONL; other formats are silently ignored. The scrub deletes the raw export, and blob soft delete keeps it only 7 days (storage.bicep:38-46), so the 2026-10-07 export no longer exists in Azure.
- On client-s a fiche id is the document's file name when its number has fewer than 5 digits ('KB0233 - Associate a phone line': double space, sometimes an en dash), and review decisions are keyed by the sha256 of the EXTRACTED text. Restore Kbs/ with identical names and bytes and keep python-docx 1.2.0 / pypdf 6.18.0 pinned. Otherwise labels, reference questions and review decisions stop matching.
- app/app.py:173 hard-codes _STORAGE_ACCOUNT = 'stknowledgeengine3v9' for every Web App table (labels, refs, diagsessions, itsm, conversations). scripts/repair-, clear-, check- and backfill-*-transcribed*.ps1 and sync-client.ps1 hard-code it too. In a new subscription they read or write the wrong account until they are parametrized.
- kb-<client> for a real client is not in Bicep (storage.bicep creates only kb-clienta/b/c). bootstrap Confirm-KbContainer creates it; a missing container makes the indexer fail with a misleading managed-identity error. audio-raw- and video-raw- come from the bootstrap ingestion phase, and kecore- and tickets- only for the clients listed in kecore.bicep's 'clients' parameter.
- Ingestion never passes SharePoint deletions on, and the text indexer indexes .csv files. A ticket export dropped in the SharePoint library ends up in the index (runbook §17.6 and §18.8). The kb container can also hold documents deleted on the site, which still become fiches.
- Table re-import is create-only (409 = kept). The reference-question seed button (app/labels.py seed_refs) writes rows with the same deterministic RowKey, so import the backup before anyone clicks 'Importer les questions du dépôt', or the seed rows win. The seed also needs kefindfiches, which stays empty until the first kecore run publishes its catalog.
- labeled_by_id, decided_by_id, the convindex PartitionKey and the diagsessions userId hold old-tenant Entra oids: informational only in the new tenant. The labeling order is per user id (labels.py _order), so labelers get a new order.
- The Durable hub kecorehub and azure-webjobs-secrets share the storage account (host.json, AzureWebJobsStorage__accountName). Do not copy their tables, queues or containers, and do not count them as data.
- The routing work of runbook §19.20 was never deployed. Expect no kefindreview, taxonomy.json or routing/. funnel-config.json and any routing activation are tied to old run ids and maps: measure and activate again, never restore them.
- download-batch on Windows fails the whole batch on a blob name with NTFS-illegal characters or a path over 260 characters, and on an existing file unless --overwrite true. Keep the backup root short and outside the repo, and compare the listed and downloaded counts printed per container.
- Data retention after a subscription is disabled is not confirmed (runbook §19.21). Run blocks 1-3 now: they are read-only against the old account.

## webapp
- webapp.bicep's sites/config 'appsettings' rewrites the whole collection. Every infra/main.bicep run wipes KECORE_FUNCTION_URL and KECORE_FUNCTION_KEY (and any DIAG_* setting). kecore-link.bicep must be run again after it (its own header says so); otherwise from_env() returns None and the Diagnostic silently runs on the search index alone, while /dictionary and /review say 'Le moteur n'est pas relié'.
- A redeploy of main.bicep without the easyAuthClientSecret parameter sets MICROSOFT_PROVIDER_AUTHENTICATION_SECRET to '' (webapp.bicep:98, default ''), which breaks sign-in. The App Registration secret also expires (created with --years 1).
- KECORE_FUNCTION_KEY is a Key Vault reference. While App Service has not resolved it (role propagation, missing vault), the app sees the literal '@Microsoft.KeyVault(...)' and from_env() treats the engine as absent, with no error. Check 'Key Vault reference: Resolved' (runbook §19.8). kecore-link also needs kv-<prefix>-v9 to exist first (main.bicep does not create it; bootstrap-new-tenant.ps1 does), and it runs listKeys on the Function host. Deploy the Function code and let its host start first (not verified on a fresh app here).
- No table is created by Bicep. diagsessions, ticketlabels and refquestions (plus convindex/convturns and itsmtickets today) are created by the Web App at import, fail-soft. If the Storage Table Data Contributor role has not propagated at first start, create_table fails silently. From code reading, TableStore.create and AzureTable.create then raise ResourceNotFoundError: a new diagnostic shows 'Erreur technique au démarrage' and saving a label gives a 500 error, until the Web App restarts after the role is effective. Either restart after RBAC propagation, or create the tables in Bicep.
- The Web App's Table endpoint is hard-coded (app.py:173 stknowledgeengine3v9), while the Function gets KECORE_TABLE_ENDPOINT from Bicep. Both must point to the same account, or labels written by /labels are never seen by the scoreboard. bootstrap-new-tenant.ps1 checks only that answer.py contains srch-<prefix>-v9, never app.py's storage name.

A slimmed engine.<client>.yaml without those keys turns every message into 'Erreur technique (KeyError)'. Change the code before trimming the config.
- labels.py opens config/itsm.yaml at import (labels.py:54), and itsm.py needs its clientCode key. Deleting config/itsm.yaml without changing both files makes the whole app fail to start. auth.build_access_maps also raises at startup if two engine.*.yaml claim the same tenant without entraGroup.
- Easy Auth covers the whole site, /healthz included. Without a session it returns the login page, so it is not a health probe (runbook §7). The App Registration redirect URI must be https://<new web app>.azurewebsites.net/.auth/login/aad/callback, and groupMembershipClaims=SecurityGroup is required, or no group-based client or tab access resolves. ## engine
- A new Foundry account means a new endpoint host. Every record key is sha256({model: '<deployment>@<host>', ...}) (kecore/llm.py:237-246, 313-315), so nothing recorded before can be replayed and the runbook §16.3 replay parity test cannot be run. The first kecore run must use `mode: record` and pays every call again: 215 decomposition calls for the 242 client-s fiches (runbook §16.6), plus per-fiche cards, exam and pass-A calls, plus pass B. A semantic index copied from old storage would be refused at query time as `model_mismatch`, and the run would be degraded (kefind/route.py:108).
- Deployment order for the Function: 1. main.bicep (creates the plan via webapp.bicep, storage, Foundry and models, then the kecore module). 2. Let RBAC propagate. The host reports AuthorizationPermissionMismatch on AzureWebJobsStorage for about a minute (runbook 16.5). 3. scripts/deploy-kecore-function.ps1. The host must have run once before its keys exist. 4. deploy-webapp.ps1. 5. kecore-link.bicep. It needs the Key Vault, which scripts/bootstrap-new-tenant.ps1 creates by CLI, and the Function host key from step 3. 6. Wait about 120 s, then restart the Web App until the KECORE_FUNCTION_KEY reference reads `Resolved` (runbook 19.6). Redeploy kecore-link after every main.bicep or webapp.bicep…
- Right after a zip deploy, the previous host keeps answering for minutes, and the ARM function list stays empty until `syncfunctiontriggers` (runbook 16.5, 19.17). Trust only `GET /api/kecore/version` returning the shipped commit together with all 51 expected functions, which is exactly what deploy-kecore-function.ps1 waits for (up to 10 minutes).
- deploy-guard.ps1 refuses any tree that is not a clean commit equal to origin/main after a fetch. A new repository needs an `origin` remote with a `main` branch, otherwise use -AllowNotMain on purpose. Never deploy from a tree with a merge, revert or rebase in progress (incident 19.17).
- kecore.bicep sets `siteConfig.appSettings` as a complete list, so a redeploy replaces the Function's settings. Any setting added by hand (for example KECORE_AOAI_BATCH_DEPLOYMENT) is lost: put every setting in Bicep.
- KECORE_CLIENTS is built from the `clients` default in kecore.bicep (clienta, clientb, clientc, client-s); main.bicep does not pass it. A client missing from it gets 400 'unknown client' on every route, and its kecore-<client> and tickets-<client> containers are never created. kb-<client> is not created by kecore.bicep: storage.bicep creates it for clienta/b/c only, and ingestion/main.bicep creates it per client.
- The engine tables (tickets, kefindfiches, ticketlabels, refquestions, kecorescores, kefindpending, kefindreview) are created at runtime by `create_table_if_not_exists`, by both the Function and the Web App. They are not in Bicep. Their names must match `tables` in config/labels.yaml and KECORE_TICKETS_TABLE.
- Keep python-docx==1.2.0 and pypdf==6.18.0 pinned. They decide the extracted fiche text, which feeds the record keys and the review `source_sha256`. Changing them sends fiches back to review and pays calls again.
- The runtime is Python 3.11 (linuxFxVersion), while the repo's tests usually run on 3.13. Checked here: every engine file compiles under 3.11, kefind tests pass (356), and kecore_func tests pass (213) with 2 modules skipped because azure-functions is not installed for 3.11.
- Model throughput: gpt-4o is 30 kTPM by default and is shared with the Web App assistant. `llm_parallelism` defaults to 2 (maximum 8), but host.json caps activities at 4 per instance, and the B1 CPU is shared with the Web App. Do not redeploy the Function while a Durable run is in progress (runbook 19.19).
- Ticket scrub reads only `tickets-<client>/raw/*.csv` (`;` separator, EasyVista French headers), drops unknown columns, and deletes the raw blob afterwards. Runbook 15.3 still says CSV/XLSX/JSON/JSONL; that is wrong for the Function path. The operator needs Storage Blob Data Contributor to upload the export.
- The routing code (runbook §19.20: 22 routes, the routing_run orchestration, the review tab) has never run in Azure. The first deployment in the new subscription is its first real deployment: follow the §19.20 steps (routing run without measure, review, rebuild and measure, activation) and check `routing_error` on /find.
- The Function identity holds Storage Blob Data Owner and Table Data Contributor on the whole shared storage account, including every client's kb- container and the Web App's tables. Client isolation is enforced only in code: the KECORE_CLIENTS allow-list and per-client container and partition naming.
- All engine routes need a function key (`AuthLevel.FUNCTION`). Operators fetch it with `az functionapp keys list --query functionKeys.default` and pass it as `?code=`. Durable status URLs carry their own system key. Function keys are stored by the host in the shared storage account, so recreating that account invalidates the Key Vault copy: redeploy kecore-link.
- Documentation drift to fix in the new project: kecore_func/README.md says a routing lease is dead after 2 h, but the code uses LEASE_TTL_S = 4 h (routing_service.py:81). kefind/funnel_engine.py's docstring says the Function ships only kecore and kefind; it also ships scoreboard, which kefind.calibrate and funnel_engine import.

## periphery
- -SkipItsm silently locks everyone out of /labels, /dictionary and /review. Their access falls back to config/itsm.yaml 'access' (app/labels.py), and only the bootstrap itsm phase rewrites that block and creates KE-v9-itsm-agents. Without it the file keeps the old tenant/group IDs and has_tenant_and_group() matches nobody. The Diagnostic's ticket field, ServiceNow session visibility and write-back are gated the same way.
- The bootstrap does NOT deploy itsm/writeback (logic-diag-writeback-<client>), does not run enable-diagnostic-webhook.ps1, and does not run kecore-link or the kecore code deploy. If config/diag-writeback.yaml lists a client without its executor, agents' validations stay 'validé, en attente de l'exécuteur' forever.
- Any infra/main.bicep redeploy rewrites the Web App's whole appsettings collection and authsettingsV2 (webapp.bicep). That wipes DIAG_WEBHOOK_SECRET/DIAG_WEBHOOK_CLIENT, the Easy Auth excludedPaths and KECORE_FUNCTION_URL/KECORE_FUNCTION_KEY. Re-run kecore-link (and the webhook script, if kept) after every infra redeploy, or move those settings into Bicep.
- Key Vault names are global, and the disabled subscription still holds kv-knowledgeengine3-v9 and kv-ke3-itsm-delivery (soft delete), so the new deployment needs a new naming prefix. The delivery vault name is limited to 24 characters. The main vault is created by the bootstrap's az CLI (Confirm-KeyVault), not by Bicep, and only in the ingestion/audio/itsm phases; kecore-link.bicep and itsm/writeback reference it as existing.
- Graph application permissions and the Helpdesk Administrator directory role cannot be set in Bicep. grant-graph-app-roles.ps1 and setup-secret-actions.ps1 need az logged in as Global Admin or Privileged Role Admin, and take minutes to take effect (403 until then); itsm/propose is created Disabled on a first deployment (startEnabled=false). The Temporary Access Pass policy cannot be enabled with the az token (Forbidden): Entra admin center, Authentication methods, Temporary Access Pass, Enable for all users.
- ServiceNow Zurich PDI: basic-auth API calls by interactive users (admin) are blocked. For seeding, grant admin snc_basic_auth_api_access temporarily, never disable the enforcement. svc_ke_itsm must be an Internal Integration User (allowed by allow_wsao). A hibernating PDI answers 200 with HTML. The first incident insert on a freshly woken PDI can return 500 yet commit; re-run, correlation_id prevents duplicates.
- Logic App expression traps (fix them in gen_workflow.py and regenerate, never hand-edit the JSON): createArray() with no argument is invalid, use json('[]'); a body KEY starting with '@' is evaluated, write '@@odata.id'. Set trigger concurrency to 1 so runs never overlap.
- ITSM concurrency: itsm/poll MERGEs every row every 5 min, so a form must carry the proposal version (proposedAtUtc), never the row ETag (If-Match is on the ETag read in the same request). The reveal must read the vault, then claim the row, then delete; claiming first burnt a one-time secret. mfa_reset must delete an existing TAP first (one TAP per user). remove_licenses needs LicenseAssignment.ReadWrite.All.
- The 'groups' claim refreshes only at sign-in: after adding someone to KE-v9-itsm-agents (or a client group), they must sign out and in again.
- The enrichment Function key is baked into both skillsets when search/deploy.ps1 runs (and the enrichment Function must exist first, or the script throws). Recreating fn-<prefix> means re-running search/deploy.ps1 for every client. Index and skillset templates currently hard-code the aif-/fn- endpoints of the old prefix.
- Search: the Basic tier allows 3 synonym maps in total, so one shared map (syn-clienta today) serves every client, and it must exist before any index references it. Search's identity needs Cognitive Services User on the Foundry account for Document Intelligence (AIServicesByIdentity); deploy.ps1 retries that error for 10 min while the role propagates. search/deploy.ps1 and generate-synonyms.ps1 use the Search admin key, and speech-key is the Foundry key1, so local auth must stay enabled on both or those paths must move to managed identity.
- Enrichment order: an audio/video transcript can only be tagged with entities already in the client's index (facet on 'entities'). Text documents must be enriched first. The firstRunUtc offsets (ingest +1 h, audio/video +1 h 30) plus hourly indexers only approximate this on a first load.
- Ingestion Logic App traps: the HTTP action buffers at most 100 MB, so bigger files are copied with Put Block From URL. HEAD/GET on blobs with a managed-identity token needs the x-ms-version header (without it every file was re-copied daily, and flags and metadata were lost). The Blob XML listing gives an object for 1 blob and null for 0, so normalize to an array. A blob metadata PUT replaces the whole set, so always rewrite clientid. A Recurrence without a startTime fires at creation, before RBAC propagates, hence firstRunUtc.

Register Microsoft.VideoIndexer first. Reuse a video already Processed, or each daily run re-bills a full pass. Append loops must run sequentially or lines land out of order.
- External SharePoint (client-s, owner decision a): the ingestion app must be multi-tenant and have a redirect URI (https://login.microsoftonline.com/common/oauth2/nativeclient), else consent fails with AADSTS500113. Grant Sites.Selected on the site through Cloud Shell (Invoke-MgGraphRequest; Graph Explorer's permission panel is broken). Admin consent in the external tenant is a separate, often-skipped step; read success from the final URL (admin_consent=True) and use a private window. The ingestion secret is created with --years 1 and expires.
